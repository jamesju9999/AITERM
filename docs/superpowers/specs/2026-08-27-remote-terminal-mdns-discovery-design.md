# 遠端終端機共享 計畫②C：mDNS 區網自動發現 — 設計

日期：2026-08-27
狀態：待使用者核可

## 問題

計畫②的決策紀錄明確選定「連 mDNS 一起做」當作完成定義（見 `2026-08-26-remote-terminal-sharing-2-ui-design.md` 的決策紀錄表），但實際執行的四個計畫（2a-commands、2b1-viewer-client、2b2a-tab-type、2b2b-host-ui）都沒有排進 mDNS，程式碼裡留下「2C 還沒上線」的註解，是落後補做的部分。

現況：`ConnectDialog` 只能靠手動輸入 `host:port` 連線，光打 6 位短碼會被 `parseAddress` 擋下來，回報「位址格式錯誤」。

## 範圍

**含：**

- 主控端：分享中的每個短碼透過 mDNS 廣播（`_aiterm._tcp.local.`），生命週期跟著 `start_share`/`stop_share` 走
- 觀看端：`ConnectDialog` 送出時若手動位址未填，先用短碼查詢 mDNS，成功就直接連，失敗依原因給對應提示
- 新增一個 Tauri command 封裝查詢邏輯（找到一台／找不到／找到多台三種結果）

**不含：**

- 計畫③A（觀看端 UI/UX 完整對等）——獨立子專案，互不阻塞
- 跨網段、VPN、非同區網的發現方式——超出 mDNS 本身的能力範圍

## 套件選擇

用 `mdns-sd`（純 Rust 實作的 mDNS/DNS-SD，macOS 用 dns-sd、Linux 用 Avahi、Windows 環境都驗證過相容，不需要額外安裝 Bonjour 或系統服務）。符合這個專案「macOS/Windows/Linux 都要能動，不能只在裝了某個系統服務的機器上才行」的跨平台要求。

## 廣播內容與生命週期

**服務名稱刻意不用 6 位短碼本身，短碼放在 TXT 記錄裡。**

原本設想「兩台機器剛好選到同一組短碼」時，觀看端會同時收到兩個 mDNS 回應，可以據此判斷成衝突、要求改用手動位址。但 `mdns-sd` 遵守 RFC 6762 第 9 節：當兩台機器搶註冊同一個服務名稱時，套件會自動幫其中一台改名（`DaemonEvent::NameChange`），不會讓兩邊同時廣播成功——衝突在**廣播端**就被協定悄悄吃掉了，觀看端根本看不到「兩個回應」，原本設想的判斷點會失效。

修正：服務名稱用一個不會撞名的隨機值（例如 UUID），6 位短碼放進 TXT 記錄的 `code` 欄位。觀看端瀏覽所有 `_aiterm._tcp.local.` 服務，用 TXT 裡的 `code` 去比對使用者輸入的短碼，在一個收集時間窗（1.5 秒）內累積所有比對上的結果——「一台／零台／多台」的判斷權完全在觀看端手上，不會被協定層的改名機制打斷。最終呈現給使用者的行為（找到一個就連、零個退回手動、多個要求手動）跟原本核准的決策一致，只是換了一個不會被協定打斷的實作方式。

廣播內容只有 TXT 裡的 `code`，不含分頁標題、使用者名稱、cwd——延續原 spec「找到多台機器回應同一組短碼時直接要求改用手動位址」與「不廣播內容」的隱私限制。

生命週期：

- `start_share` 產生新短碼時，同時用該短碼註冊一筆 mDNS 服務（TXT 帶那組短碼）。`start_share` 本身是冪等的（同一個分頁重複呼叫回傳既有短碼、不做事）——mDNS 註冊要跟著同一個冪等判斷走，只在真的產生新短碼的那個分支才註冊，不能每次呼叫都重新註冊一次
- `stop_share` 時，取消註冊對應那一筆
- mDNS 背景執行緒（`ServiceDaemon`）跟著 WS server 的 `start_if_needed`/`stop_if_idle` 一起啟停——沒有任何分頁在分享時，不會多開一個行程在背景廣播

## 觀看端查找流程

新增一個 Tauri command 封裝查詢邏輯：

```rust
pub enum DiscoverResult {
    Found { host: String, port: u16 },
    NotFound,
    Ambiguous,
}

#[tauri::command]
pub async fn share_discover(code: String) -> Result<DiscoverResult, String>
```

`ConnectDialog` 的 `submit()` 改成：

- **手動位址欄位沒有展開／填寫**：先呼叫 `share_discover(code)`，畫面顯示「搜尋中…」。
  - `Found`：直接用回傳的 host:port 呼叫 `shareViewerConnect`，使用者完全不用碰位址欄位——這是「打 6 位數就能連」的路徑。
  - `NotFound`：展開手動欄位，顯示「在這個網路上找不到這組編號。可能已失效，或你們不在同一個網路。請對方唸出他畫面上的位址：」（沿用計畫②spec 原本的文案）。
  - `Ambiguous`：展開手動欄位，顯示「這個網路上有不只一台機器在用這組編號，請改用手動位址確認是哪一台」——跟「找不到」用不同句子，這是「有找到但無法判斷是哪一台」，不是真的找不到，混用文案會誤導使用者以為對方沒在分享。
- **手動位址欄位已經展開且有填**：完全不跑 mDNS 查詢，直接用使用者輸入的位址連——手動永遠優先，不會被搜尋卡住或蓋掉使用者已經輸入的內容。

## 錯誤處理

| 情境 | 使用者看到 |
|---|---|
| 查到一台 | 直接連線，不額外顯示訊息 |
| 查無 | 展開手動欄位＋「找不到這組編號」文案 |
| 查到多台 | 展開手動欄位＋「有不只一台機器在用這組編號」文案 |
| 網路擋 multicast（既有已知限制） | 表現跟「查無」一樣（查詢逾時收不到任何回應），靠手動位址退路救 |

## 測試

- Rust 端：`mdns-sd` 允許在測試行程裡自己註冊/瀏覽服務，不需要真的兩台機器。針對 `share_discover` 寫三個情境各一個測試：註冊 0 筆（`NotFound`）、註冊 1 筆帶對應 TXT code（`Found`）、註冊 2 筆帶同一個 TXT code（`Ambiguous`）。
- 前端：`ConnectDialog` 新增測試比照現有寫法（mock IPC），斷言三種 `DiscoverResult` 分別對到正確的畫面分支與文案。
- 手動驗證（自動化測不到）：兩台實機下，主控端分享、觀看端只打短碼（不碰手動欄位）驗證能連上；關掉其中一台的 Wi-Fi 多播（若環境允許）驗證會退回手動並顯示正確文案。

## 已知限制

| 限制 | 說明 |
|---|---|
| 部分 CI 沙箱環境不允許 multicast | Rust 端三個新測試可能需要標記 `#[ignore]`（`cargo test` 目前已有 3 個 ignored 的先例），這是環境限制，不是測試沒寫 |
| mDNS 在擋多播的網路上失效 | 沿用計畫②spec 既有的已知限制：靠手動位址退路救；若連直連都被防火牆擋則完全不通 |
| 防火牆 | 沿用計畫②spec：事前提醒，不偵測不阻擋。Windows 首次啟用分享時系統可能跳出網路存取詢問，這條路徑目前仍未在防火牆開啟的機器上實測過（同計畫②spec 的已知限制） |
