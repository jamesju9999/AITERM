# 規格拆出的實作卡：相依關係與開工前合併 — 設計

日期：2026-10-16
狀態：使用者同意（「兩步一起做」；派工資訊放活動記錄、不加調度員節點）

## 問題（實際發生過）

PingPon 專案裡，「整合：組裝 main.ts」派給了工程師3，但它要組裝的 ai／audio／storage／鍵盤輸入／特效
是工程師2 做的。各工程師的分支彼此獨立（工程師3 的分支不含工程師2 的任何 commit），工程師3 看不到那些程式碼，
於是在修正輪自己又寫了一套（兩份差約 900 行），最後由協調者合併時二選一。一半的工作重複，留下的版本也沒有經過審查。

根因：拆卡格式沒有相依關係；派工只看「誰最閒」；開工時工作資料夾不含別人的成果；閒置工程師也可能接走有前置的卡。

## 設計

### 1. 拆卡格式：`depends_on`

`tasks.json` 每個任務可以有 `depends_on`：依賴的**前面**任務的索引（0 起算）。

```json
{"tasks": [
  {"title": "audio 模組", "body": "…"},
  {"title": "storage 模組", "body": "…"},
  {"title": "整合 main.ts", "body": "…", "depends_on": [0, 1]}
]}
```

- 協調者的拆卡提示加上說明：需要用到前面任務程式碼的任務要列出來；整合類任務依賴它要組裝的所有模組；被依賴的放前面。
- 驗證：索引必須小於自己的位置（不可自己、不可往後、不可超出範圍），否則拆解卡判失敗並寫出原因（跟現在格式錯誤同樣處理）。
- 沒有 `depends_on`（舊格式）＝沒有相依，行為與現在相同。
- 存放：`tasks.depends_on` 欄位，JSON 陣列，內容是實作卡的 task id（拆解時把索引換成 id）。

### 2. 派給誰

一律照忙碌程度派給最閒的工程師，有沒有相依都一樣。前置在別人手上的卡靠第 3、4 節（等審過＋開工前合併）保證正確。

> 修訂（2026-10-16 實機）：原本「有相依就派給擁有最多前置的工程師」。Pomodoro 測試中每張卡都依賴「專案骨架」，
> 結果 13 張全部堆在同一人身上、另一位工程師完全沒工作。共同的地基會把所有相依卡吸到同一人，所以改回照忙碌程度分。

### 3. 什麼時候可以開工（排程器）

一張卡的前置分成兩種：
- **同一位工程師的**：不用等，佇列順序本來就保證前置先做（前置一定排在前面；退回修正的卡也插在最前面）。
- **別位工程師的**：要等那些前置模組**審查通過**（`module_state == Passed`，含手動放行）才能開工。

還不能開工的卡，排程器跳過它，改看同一位工程師佇列裡的下一張，不會卡住整條佇列。

### 4. 開工前合併

可以開工、而且有別位工程師前置的卡，派工時在建立／取得工作資料夾之後、記錄 `start_sha` 之前：
- 對每個別位工程師的前置，把它**通過審查的版本**（通過那張審查卡的 `end_sha`；沒有審查者或手動放行時，用該模組鏈最後一張成功的 work/fix 卡的 `end_sha`）
  `git merge --no-edit -m "Merge 前置：<標題>"` 進這位工程師的工作資料夾。
- 用的是審過的版本，不是對方分支的最新 HEAD（那上面可能有還沒審的卡）。
- `start_sha` 在合併之後才記，所以審核者審的範圍只有這張卡自己的改動。
- 合併有衝突：`git merge --abort` 還原，這次派工失敗、工程師暫停，錯誤訊息列出衝突的檔案；使用者處理後按「重試」再合一次。

### 5. 重新分配（閒置工程師接卡）

只搬**前置都已通過審查**的卡（前置本來就在接手者身上的也算）：接過去馬上能開工，開工前把前置合併進來。
被別張卡依賴的卡也可以搬——依賴它的卡會改成等它審過。前置還沒通過的卡不搬（接過去也只能乾等）。

### 6. 畫面

- 前端 `TaskRow` 多一個 `depends_on`。
- 工程師卡上，還在等別位工程師前置的模組 chip 顯示「⛓」，滑過顯示「等前置模組：A、B」。

### 7. 看得到是誰在派工（不加「調度員」節點）

派工由 AITerm 的程式決定，不是協調者。為了不讓畫面更擠，資訊放在發生的地方：
- 活動記錄多三種事件：
  - 派工：「派工：整合 main.ts → 工程師3」（規格拆出的卡建立時；時間＝`created_at`，對象＝原始負責人）
  - 重新分配：「重新分配：storage 模組 從工程師2 移給 工程師3」（新欄位 `assigned_from`、`assigned_at`）
  - 開工前合併：「開工前合併：把 audio、storage 合進工程師3」（新欄位 `premerged`，JSON 陣列存合進來的前置卡 id；時間＝`dispatched_at`）
- 協調者 → 工程師的派工虛線滑過時顯示說明：「協調者拆好的任務，由系統依忙碌程度與相依關係分派」。

## 不做

- 獨立的「調度員」節點（畫面會更擠；之後真的需要再加，不影響本功能）。

- 協調者指定由哪位工程師負責（理由：拆卡當下看不到之後加入的人；模型挑人不穩定）。
- 跨專案相依、手動指派卡片的相依（只處理規格拆出的卡）。

## 測試

- Rust：`depends_on` 解析與驗證（往後／自己／超出範圍報錯、舊格式）；派工選人（同擁有者集中、平手選最閒）；
  `depends_on` 存成 id；排程器跳過等待中的卡、改派同一位的下一張；前置通過後可開工；
  開工前合併把審過的版本合進來、`start_sha` 在合併後；衝突時還原並失敗；重新分配不搬有相依或被依賴的卡；欄位遷移。
- 前端：等前置的 chip 顯示 ⛓ 與前置名稱。
- 實機：用假 claude 跑一份含整合任務的規格，確認整合卡等到前置通過才開工，而且工作資料夾裡有前置模組的檔案。
