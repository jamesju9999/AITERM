# AITerm 遠端終端機共享 — 設計

日期：2026-08-26
狀態：待使用者核可

## 問題

團隊每個人都在自己的 AITerm 裡開 Claude Code CLI，但彼此之間沒有任何協作管道。brainstorm 中確認的痛點是兩個：**看不到彼此在做什麼**、**無法互相分派/交接**。過程中使用者追加了第三項需求，並確認它的優先度最高：

> 可以連線至另一個正在執行的 AITerm 終端機視窗，看到該畫面並且可以控制。每個終端機都有一個獨立的編號，把編號給同事輸入就能連進去。

本 spec 只做這一項。

## 範圍界定：這是三個子系統，本 spec 只涵蓋 S1

| | 子系統 | 核心難點 | 狀態 |
|---|---|---|---|
| **S1** | **遠端終端機共享**：用編號連進另一台 AITerm 的終端機分頁，看畫面＋可控制 | 跨機器低延遲雙向 PTY 串流、輸出多路 fan-out、「別人能在我電腦上打字」的信任模型 | **本 spec** |
| S2 | 跨機器 presence：誰在線、在哪個 repo/分支、忙/卡/閒 | 區網自動發現、狀態廣播、離線者狀態空白 | 留給後續獨立 spec |
| S3 | 任務分派/交接：任務進隊友的 AITerm，他按「接受」才注入他的 Claude CLI | 任務封包格式、收件匣 UI、注入既有 agent 分頁 | 留給後續獨立 spec |

**為什麼先做 S1**：S1 的傳輸需求（低延遲、雙向、串流）是 S2/S3 的超集。若先做 S2，它會蓋在一條輪詢式管道上，等 S1 來了整條要打掉重做。S1 做完後，S2 幾乎是同一條連線多送一個狀態封包，S3 也退化成很薄的一層。

另外，S1 是三者中唯一**不需要自動發現機制也能成立**的——編號本身就同時是地址與配對憑證。S2/S3 因為要「持續知道誰在線上」才非有發現機制不可。

**明確不含：**

- S2、S3 的任何部分
- 跨網段、VPN、遠端（非同區網）連線——見「已知限制」
- 中繼伺服器、任何需要有人維運的中央主機
- 分享**整個 AITerm 視窗**或終端機以外的分頁（資料庫、知識庫、AI 面板等）——共享單位是單一終端機分頁
- 觀看端錄影/回放存檔
- 螢幕影像串流（明確否決，理由見「架構」）

## 決策紀錄

以下都是使用者在 brainstorm 中明確選定的，實作時不要「順手改回來」：

| 決策 | 選定 | 備註 |
|---|---|---|
| 三個子系統先做哪塊 | **S1 遠端終端機共享** | 作者推薦並獲採納 |
| 共享單位 | **單一終端機分頁**，每個分頁各有自己的編號 | 使用者可只分享跑 Claude CLI 的那個分頁，其他分頁同事看不到 |
| 部署形態 | **同區網、不架伺服器** | 分享方的 AITerm 在分享期間自己就是 server |
| 連線門檻 | **每次都要主控端按同意** | 編號只負責「找得到你」，真正的門是即時同意 |
| 控制權授予 | **同意當下就選：只能看 / 可以控制** | 一次決定，不走「先唯讀再請求控制」的兩段式 |
| 編號形式 | **6 位數字短碼**，靠區網自動發現找到位址 | 短到可以用喊的 |
| 手動位址退路 | **要** | 使用者最初選純短碼，後續討論到公司網路可能擋多播後確認補上 |

| 防同區網中間人 | **TLS ＋ 4 位驗證碼人工核對（SAS）**，不用 PAKE | 2026-08-26 於 writing-plans 階段實測 crate 後決定：`spake2` 僅有 pre-release 版，不押在安全關鍵路徑上 |
| 實作計畫切分 | **拆成三份依序執行**：①後端傳輸地基 ②前端兩側 UI（先用手動位址就能跑）③區網自動發現 | 每一份都是可獨立驗證的完整成果；mDNS 排最後，前兩份靠手動位址即可端到端實測 |

## 現況調查（設計的事實基礎）

以下都是實際讀過程式碼／查過套件原始碼確認的，不是推測：

| 事實 | 位置 |
|---|---|
| `PtySession` 的輸出目前只有**單一出口**：`spawn`/`spawn_with_id` 各吃一個 `on_data` callback，reader 執行緒只呼叫它一次 | `src-tauri/src/pty/session.rs:274`、`:426` |
| `output_ring` 存的是**原始 PTY bytes**；ANSI 是 `get_recent_output` 讀取時才 strip 的 | `src-tauri/src/pty/session.rs:108`、`:716-727` |
| `PtyManager` 已有 `write`、`resize`，輸入與尺寸變更可直接重用，不需新開寫入路徑 | `src-tauri/src/pty/manager.rs:75`、`:79` |
| 既有兩個 axum server（Claude Code 橋接、MCP 工具 server）**都只綁 `127.0.0.1`** | `src-tauri/src/bridge/mod.rs:68`、`src-tauri/src/mcp_server/mod.rs:84` |
| MCP 工具 server 上掛著 `execute_query`（明文允許任意 SQL，含 INSERT/UPDATE/DELETE/DDL）與知識庫工具 | `src-tauri/src/mcp_server/tools.rs:223` |
| `axum 0.8` 已是直接依賴；其 `default` features 為 `form/http1/json/matched-path/original-uri/query/tokio/tower-log/tracing`，**不含 `ws`** | `src-tauri/Cargo.toml:46`；`axum-0.8.9/Cargo.toml:81-91` |
| `PtyManager` 已是 `Arc` 共用（agent 協調功能所需），MCP server 與主 app 用同一份——共享 server 可直接取得同一份，不需再改動 12 個呼叫點 | `src-tauri/src/lib.rs:175`、`:245`、`src-tauri/src/pty/commands.rs:28` 等 |
| 前端不卸載非作用中的終端機分頁（用 `visibility: hidden`），因為 xterm.js 在沒有尺寸的元素上 resize 會爆 | `CLAUDE.md`、`src/components/TerminalView.tsx` |

**結論**：輸出的重播能力（raw ring buffer）、輸入的寫入路徑（`PtyManager::write`）、HTTP server 的框架（axum）三塊底子都已經在了。真正要新建的是「多路 fan-out」、「一個對區網開放的服務」與「配對／同意的信任模型」。

## 使用流程

### 分享方

1. 在終端機分頁的右鍵選單／分頁列按「分享這個分頁」。
2. AITerm 當場啟動共享 server（綁區網介面）、產生一組 **6 位短碼**、在區網廣播「短碼 → 位址」。UI 同時顯示自己的 `host:port`，供自動發現失效時對方手動輸入。
3. 分頁標題列出現明顯的分享中徽章，旁邊是觀看者清單。
4. 有人輸入短碼時跳出同意視窗：「**OOO 想連進這個分頁**」、一組 **4 位驗證碼**（請對方唸出他畫面上的數字核對，見「安全契約」第 2 點），以及兩顆按鈕：**只能看** / **可以控制**。
5. 連上後隨時可以：收回某人的控制權、單獨踢掉某人、或停止分享（server 關閉、短碼立即失效、所有人斷線）。

**短碼的生命週期**：按下分享才存在，停止分享就作廢。分頁平常沒有編號。

### 觀看方

1. 新分頁選單多一個「連線到同事的終端機」，輸入 6 位短碼（或展開「或直接輸入位址」貼上 `host:port`）。
2. 畫面顯示自己這端算出的 **4 位驗證碼**，並提示「請把這組數字唸給對方核對」，同時顯示「等待對方同意」。
3. 對方按同意後，開一個 `remote-terminal` 分頁；先收到 ring buffer 重播補上歷史，之後接即時串流。
4. 唯讀模式下分頁明確標示「唯讀」，按鍵根本不送出去（不是送了被拒絕）。

## 架構

### 這是 AITerm 第一個對區網開放的服務——所以它必須獨立

新開第三個 axum server（`src-tauri/src/share/`），**不**掛在既有的 `bridge` 或 `mcp_server` 上。

理由不是模組潔癖，是暴露面。那兩個 server 綁 `127.0.0.1`，共享服務則必須綁區網介面。若為了省事把路由掛進 `mcp_server`，等於順手把 `execute_query`（允許任意 SQL）和知識庫工具一併暴露到辦公室網路——這個代價不能接受。兩者的信任模型也完全不同：MCP server 用固定 token 閘門，共享服務用「短碼 ＋ 每次即時同意」。

**預設完全不監聽**：只有使用者按下某分頁的「分享」時才啟動 server 並開始廣播；最後一個分享停止時 server 關閉。沒在分享時，AITerm 在區網上一個 port 都不開。

### 資料流

```
主控端 AITerm                                    觀看端 AITerm
┌──────────────────────────┐                    ┌────────────────────────┐
│ PtySession reader 執行緒   │                    │ remote-terminal 分頁    │
│   │                      │                    │      xterm.js          │
│   ├─→ 既有 on_data ───────┼→ 自己的畫面           │       ▲       │        │
│   │   (pty://data/…)     │                    │       │       ▼        │
│   └─→ broadcast(新增) ────┼──── WebSocket ─────┼───────┘   按鍵上行      │
│                          │  輸出下行 / 輸入上行   │                        │
│   PtyManager::write ←────┼────────────────────┼────────────────────────┘
└──────────────────────────┘
```

三個要點：

1. **PTY 輸出改成 fan-out，但既有路徑一個字都不動。** 不改 `on_data` 的簽名，而是在 reader 執行緒既有的呼叫點旁邊多加一次 `tokio::sync::broadcast` 送出。沒有訂閱者時 broadcast send 幾乎零成本——不使用分享功能的使用者完全不受影響。
2. **傳的是原始 PTY bytes，不是畫面影像。** 頻寬等於終端機輸出本身（平常幾 KB/s），而且觀看端拿到的是**真的終端機**：可選字複製、可捲動、可搜尋。影像串流那條路明確否決（頻寬大、文字糊、不能複製）。
3. **輸入走回既有的 `PtyManager::write`。** 觀看端按的鍵跟主控端自己打字走同一個入口，不新開寫入路徑。

### WebSocket，不用 SSE

需要雙向（輸出下行、按鍵上行）。打開 `axum` 的 `ws` feature 即可，**不新增任何 crate**。

### 短碼、發現與手動退路

- 按下分享時產生 **6 位數字短碼**，並在區網廣播「短碼 → 位址」。短碼只在分享期間存在，停止分享立即作廢；分頁平常沒有編號。
- 觀看端輸入短碼 → 從區網廣播解析出位址 → 發起連線。
- **手動退路**：短碼輸入框旁提供「或直接輸入位址」，接受 `host:port` 形式。這是為了公司網路擋多播、跨 VLAN、無線訪客網路這類自動發現失效的環境保留的唯一生路。主控端 UI 在顯示短碼的同時也要顯示自己的 `host:port`，否則使用者無從取得要貼的位址。
- 具體的發現機制（mDNS 服務註冊 vs 自製 UDP 多播查詢）留給 writing-plans 階段依 crate 可用性與跨平台實測決定。本 spec 只定義行為契約：**輸入短碼能在同區網找到對方；找不到時 UI 明確告知並引導使用手動位址**，而不是無聲失敗或無限轉圈。

### 觀看端是新的分頁型別

新增 `remote-terminal` 分頁型別，**不重用既有的 `terminal` 型別**。理由：`terminal` 分頁的整套邏輯都假設背後有一個本機 PTY session（cwd 追蹤、書籤、AI 面板的指令注入、close guard、agent mission），遠端分頁一個都沒有。混用會踩到一連串隱性假設。

（既有教訓：側邊欄的「Agent: xxx」分頁實際型別是 `terminal` 而非 `code-assistant`，型別判斷搞錯曾造成整套分頁邏輯做錯。新型別要在所有既有的分頁型別分支上被明確處理，包含 close guard。）

### 尺寸由主控端說了算

觀看端的 xterm.js 依**主控端的 cols/rows** 建立，並自動縮小字級以塞進自己的視窗；真的塞不下就給捲軸。主控端 resize 時廣播一則 resize 訊息，觀看端重新 fit。

理由：主控端正在工作，不該因為別人連進來而版面跳動。這也避開了「觀看端 resize 反向改動主控端 PTY」這條會互相打架的路徑——觀看端**永遠不會**觸發 `PtyManager::resize`。

### 控制權：一支麥克風

- 任何時刻最多**一個**遠端持有控制權，其餘一律唯讀。
- 主控端本人永遠能打字（機器是他的）。
- 要把控制權從 A 轉給 B，必須先收回 A 的。
- 唯讀端的按鍵**根本不送出**（不是送了被伺服器拒絕），且分頁明確標示「唯讀」。

### 慢速觀看端必須重新同步，不能靜默漏資料

`tokio::sync::broadcast` 在訂閱者太慢時會丟棄舊訊息並回報 `Lagged`。終端機**不能容忍漏 bytes**：ANSI 逃脫序列被從中截斷，畫面就從此錯亂且不會自己好。

因此規定：觀看端收到 `Lagged` 時，不是忽略，而是**清空畫面、重新用 ring buffer 全量重播一次**再接回即時串流。寧可閃一下，也不要帶著壞掉的畫面繼續。

### 新連線的畫面補齊

觀看端一連上，先收到主控端 `output_ring` 的**原始 bytes** 全量重播（需在 `PtySession` 新增一個不 strip ANSI 的 `get_recent_raw`，既有的 `get_recent_output` 維持原樣不動），之後才接即時串流。

### 主控端的可見提示是安全需求，不是裝飾

分頁標題列出現**明顯的分享中徽章**，旁邊是觀看者清單（誰在看、誰持有控制權）。使用者必須隨時一眼看出有人在看自己的終端機。提供：收回某人的控制權、單獨踢掉某人、停止分享（server 關閉、短碼作廢、所有人斷線）。

## 安全契約

本 spec 定義行為契約；具體密碼學選型留給 writing-plans 階段實測 crate 後決定（比照 2026-08-17 vcs spec 處理「draft→ready 走 REST 還是 GraphQL」的作法）。

1. **傳輸必須加密。** PTY 內容可能含 API key、原始碼、`.env` 內容，區網明文不可接受。
2. **必須防冒充——用 4 位驗證碼人工核對（SAS）。** 光靠自簽憑證擋不住同區網的中間人：觀看端沒有任何先驗資訊可判斷該信任哪張憑證。6 位短碼本身熵太低（10⁶），直接拿來當金鑰的話，中間人錄下交握後可離線暴力破解，等於防不住。

   選定作法：**TLS 1.3（自簽臨時憑證）＋ RFC 5705 匯出金鑰material 導出的 4 位驗證碼**。雙方畫面各自顯示這 4 位數，主控端按同意前口頭核對一句「你那邊是幾號？」。中間人必須同時維持兩條獨立的 TLS 連線，兩邊導出的驗證碼必然不同，對不上就是有人在中間。

   選這條而不是 PAKE（SPAKE2）的理由：`rustls 0.23` 與 `tokio-rustls 0.26` **已經在 `Cargo.lock` 裡**（`reqwest` 的 `rustls-tls` 帶進來的），而 `spake2` crate 目前只有 pre-release 版（0.5.0-pre.0），不適合押在安全關鍵路徑上。代價是多一句口頭確認——但使用者本來就得把短碼講給對方，這句話搭在同一次對話裡。
3. **短碼被猜中不構成入侵。** 還有「每次都要主控端按同意」那道門。這是「每次同意」這個決策直接換來的好處，讓短碼可以短到能用喊的。
4. **輸入來源必須經過授權檢查。** 只有當前持有控制權的那一條連線送來的按鍵才會進入 `PtyManager::write`；唯讀連線送來的一律丟棄（即使觀看端理應根本不送）。這道檢查在**伺服器端**，不能只依賴觀看端自律。
5. **共享 server 只在分享期間存在。** 沒有常駐監聽，沒有「忘了關」的長期暴露面。

## 錯誤處理

沿用專案既有模式，不重造一套：

- **短碼找不到對方**（自動發現失效或對方已停止分享）→ 明確告知「找不到這組編號，可能已失效，或你們不在同一個網路」，並引導使用手動位址。不無聲失敗、不無限轉圈。
- **對方拒絕連線**→ 觀看端顯示「對方未同意」並關閉待連分頁，不留半開狀態。
- **對方遲遲不回應**→ 主控端的同意彈窗**不自動拒絕**（使用者可能只是走開了，自動拒絕會讓他回來時毫無線索）。觀看端則顯示「等待對方同意」並隨時可取消；等待逾 60 秒後改顯示「對方可能不在位子上」，但連線請求仍保留，直到觀看端取消或主控端回應為止。
- **主控端中途停止分享、關閉分頁、關閉 AITerm、電腦睡著**→ 觀看端分頁顯示「連線已中斷」並停止渲染，保留最後畫面供閱讀，不清空、不崩潰。**不自動重連**（短碼已作廢，重連無意義）。
- **主控端的 PTY session 結束**（shell 退出）→ 等同上一項。
- **綁定 port 失敗**（被占用）→ 比照既有兩個 server 的作法：照實顯示錯誤並提示到設定裡換一個埠。
- **觀看端跟不上（`Lagged`）**→ 不是錯誤，是已定義行為：清空重播（見架構）。
- **同時有第二人請求控制權**→ 明確回覆「目前控制權在 OOO 身上」，不靜默降級成唯讀。

## 測試

比照專案既有慣例：

- **Rust 單元測試**：`PtySession` 的 broadcast fan-out——沒有訂閱者時既有 `on_data` 行為完全不變；有 N 個訂閱者時每個都收到完整且相同的 bytes。
- **Rust 單元測試**：`get_recent_raw` 回傳未經 ANSI strip 的原始 bytes，且既有 `get_recent_output` 的輸出不受影響（防迴歸）。
- **Rust 單元測試**：控制權狀態機——同時只有一人能持有；唯讀連線送來的輸入被丟棄而非寫入 PTY；控制權轉移必須先收回。
- **Rust 整合測試**：比照既有 `tests/mcp_tool_server.rs` 的手法起一個共享 server，跑「連線 → 待同意 → 同意（唯讀）→ 收到重播與即時輸出 → 送輸入被拒 → 升為可控制 → 送輸入寫進 PTY → 主控端停止分享 → 連線乾淨關閉」整條路徑。
- **Rust 整合測試**：短碼作廢後用同一組短碼連線必須失敗。
- **前端（Vitest + Testing Library）**：分享對話框與觀看者清單、同意彈窗的兩顆按鈕、唯讀分頁不送出按鍵、連線中斷後保留最後畫面。mock IPC 呼叫，比照 `src/components/KnowledgeBaseView/NotebookSidebar.test.tsx`。
- **前端**：`remote-terminal` 新分頁型別在所有既有分頁型別分支（含 close guard）都有被處理，不會掉進 `terminal` 的假設。
- **手動驗證**（自動化測不到的）：兩台實體機器同區網，實測分享跑著 Claude Code CLI 的分頁、對方連入、接手打字、TUI 程式（vim）的重播表現、以及主控端關 app 時觀看端的行為。

## 已知限制

誠實記錄，UI 文案要據實告知，不假裝做得到：

| 限制 | 說明 |
|---|---|
| 全螢幕 TUI 的重播不完美 | ring buffer 有大小上限。若 vim/htop 的初始重繪指令已捲出 buffer，觀看端連進去可能看到破碎畫面，要等程式下一次重繪才正常 |
| 主控端關 AITerm、關分頁或電腦睡著 → 連線直接斷 | 沒有中繼可以續命，重新分享會產生新短碼。這是「不架伺服器」的直接後果 |
| 跨網段、VPN、在家、出差 → 連不上 | 硬邊界，沒有繞路。要解需要中央伺服器或中繼，那是另一個量級的設計 |
| 公司網路擋多播 → 自動找人失效 | 靠「手動輸入位址」退路救；若連直連都被防火牆擋則完全不通 |
| 主控端 ＋ 一位控制者仍可能交錯打字 | 「一支麥克風」只排除遠端之間的交錯。主控端本人隨時能打字，字元層級的交錯要靠人協調，程式不擋 |
| 觀看端不能調整終端機尺寸 | 尺寸一律由主控端決定，觀看端只能縮字級與捲動 |
