# Agent 協作：舊系統轉換專案的缺項清單

日期：2026-10-20　狀態：待排程（尚未實作）
依據：以 HTBTW（IBM EGL＋Ares 桌面程式 → Angular＋Spring Boot）為實例的盤點，使用者將在 **Windows 版 AITerm** 執行。

## 背景

HTBTW 的轉換方式不是「逐支翻譯畫面」，而是 AI 撰寫**轉換工具與執行環境**：

- `tools/gen_*.py` 從舊程式產生畫面契約、流程契約、後端程式、SQL 與記錄格式。
- 533 支畫面由同一個 renderer 依契約畫出（紅線 4「畫面不手刻」），後端程式照翻產生（ADR-0007）。
- 舊系統的 EGL 執行期直接跑出黃金答案（`egl-oracle`）比對語意。
- 285 個 commit 有 230 個由 Claude 共同撰寫。

因此這類專案的瓶頸是**產生器的正確性、逐支實測、業務裁定**，不是寫程式的人手。修一個行為差異多半要改共用的產生器與執行環境，多位工程師平行改同一批檔案容易衝突。

## 什麼時候用單一 session 就好

| 情境 | 適合 |
|---|---|
| 一次一支或一小批畫面，使用者在旁回答、每支都要親自操作確認 | 單一 Claude Code session＋subagent（HTBTW 的 AC、CM 即是如此完成） |
| 規格與裁定已穩定、要大量處理、可以無人看管跑一晚、需要固定的審查與驗收 | AITerm Agent 協作 |

單一 session 不需要下表的 #1、#2、#6（直接繼承終端機的環境變數、共用同一個資料夾的相依套件、沒有深層的工作副本路徑），但沒有排程佇列、額度與重啟續跑、固定的品管交接、看板與活動記錄，對話記憶也有上限。

## 轉換專案的三個階段：哪些交給 Agent 協作

HTBTW「用產生器轉換」的做法，是在單一 session 裡盤點整個舊系統、釐清架構之後才由 AI 決定的。
這類跨模組的綜合判斷需要同一個 Agent 握著全部脈絡，不適合拆給多位 Agent。

| 階段 | 工作 | 用什麼 |
|---|---|---|
| 1. 盤點 | 依模組盤點畫面、程式、資料表、呼叫關係、編碼與風險 | **Agent 協作**：內建範本「舊系統盤點」（已完成，見下） |
| 2. 架構與策略、第一條垂直切片、產生器雛形 | 綜合判斷、與使用者來回討論、試錯轉向 | **單一 session** |
| 3. 量產與實測 | 套產生器、逐支實測、修差異 | **Agent 協作**（一位產生器工程師＋多位測試工程師；見缺項 #3） |

已完成（2026-10-20）：

- 內建團隊範本「舊系統盤點」：三位研究工程師（只讀參考資料夾、只寫文件、結論附來源路徑）、
  一位彙整工程師（整合成總覽與風險清單）、文件審核者（檢查引用與涵蓋項目）、協調者（合併文件）；不需要驗收者。
- 新增模組的「舊系統盤點」卡片範本：一鍵帶入標題與內文（範圍、資料、呼叫關係、特殊寫法與風險、轉換建議；
  產出 `docs/inventory/<模組>.md`），各研究工程師的產出格式一致，彙整時接得起來。
- 尚缺：彙整卡要等全部盤點卡合併後才該開工，目前手動建立的模組沒有設定相依的介面，要使用者在盤點完成後再指派。

## 缺項（依優先順序）

| # | 缺項 | 為什麼需要（HTBTW 實例） | 現況 | 建議做法 |
|---|---|---|---|---|
| 1 | **專案環境變數（含機密）** | 驗收者要啟動後端與實測：`DB_HOST`／`DB_USER`／`DB_PASSWORD`、`LIVE_USER`／`LIVE_PW`、`HTBTW_SOURCE` | 只有 Codex 卡能帶環境變數；Claude 卡沒有 | 專案層級設定，機密存 OS 鑰匙圈，派工時注入行程環境，不寫進提示詞與檔案 |
| 2 | **工作副本開工前的準備指令** | 每個工作副本沒有 `node_modules`、Maven 快取；每次重裝又慢又佔空間（HTBTW_Web 含相依約 1.6 GB） | 無 | 專案可設一段準備指令（例如連結主程式庫的 `node_modules`、`npm ci`），建立工作副本後自動執行 |
| 3 | **平行實測（只測不改）** | 主要工作量是逐支畫面實際操作、截圖、找出與舊系統的行為差異（UAT 清單 AC 就有 146 支） | 一個專案只能有一位驗收者，且只在協調者合併後才開工 | 新的工作種類「實測卡」：多位驗收者同時各測一批現有畫面，不改程式、不需要合併；回報差異（含截圖、重現步驟）並可轉成修正卡給負責產生器的工程師 |
| 4 | **Windows 長路徑** | 工作副本路徑「看板專案／agents／<id>／worktree／frontend／node_modules／…」容易超過 260 字元，git、npm 會失敗 | 未處理 | 建立工作副本時開啟 `core.longpaths`；縮短 agents／worktree 資料夾名稱 |
| 5 | **批次建立模組** | 轉換專案動輒數百支畫面（FR 有 827 支），逐張新增不實際 | 只能逐張建，或靠規格先行由協調者拆 | 從清單匯入（CSV，例如 `UAT-TestList.csv`，或畫面盤點），可帶標籤與相依關係 |
| 6 | **決策記憶** | ADR-0008 還有 24 項待裁定；同類問題（例如「原系統的瑕疵一律照舊」）答過就不該再問 | ask_human 的答案只回到那一張卡 | 回答過的決策累積成專案決策清單，之後每張卡自動附上；可匯出回寫到專案文件 |
| 7 | **每位 Agent 的埠號隔離** | 前端 proxy 寫死後端 8080；兩位同時啟動後端會撞埠 | 只有驗收者會挑空的埠 | 每位 Agent 分配一組埠，以環境變數傳入（搭配 #1） |
| 8 | **卡片的範圍限制** | 轉換一支畫面只該動那支的檔案；PingPon 曾發生整合卡重寫別人的程式 | 無 | 卡片寫明可改的路徑與禁止事項；審核者把改到範圍外列為必修 |
| 9 | **專案自己的審查規則** | HTBTW 有五條紅線（弱點掃描、金額不碰浮點、資料庫結構不動、畫面不手刻、自己操作一遍） | 審核者只靠通用規則與 CLAUDE.md | 讀程式庫內的審查規則檔（例如 `REVIEW.md`）附進審查提示 |
| 11 | **手動模組的相依設定** | 盤點的彙整卡要等各模組盤點合併後才開工；量產時修正卡要等實測卡 | 只有協調者拆解規格時能寫 `depends_on`，手動新增的模組沒有介面 | 新增／編輯模組時可以選「要等哪些模組完成」 |
| 10 | **模組進度總覽與 UAT 回寫** | 數百支畫面要看得到各業務模組完成比例（例如「FR 30／827」） | 只有卡片狀態 | 依標籤彙總進度；驗收與實測結果可匯出成 UAT 清單格式 |

## 建議順序

1. **#1、#2、#4**：在 Windows 上讓一張卡能完整跑完（驗收啟動得了、相依套件不必每次重裝、路徑不會過長）。
2. **#3**：這類「工具產生＋逐支實測」專案最大的加速點。
3. **#5、#6**：大量工作的進行方式（一次建很多卡、同樣的問題不再問）。
4. **#7～#10**：品質與管理，可以邊跑邊補。

## 不在 AITerm 範圍、但會影響這類專案

- 舊程式不完整：HTBTW 有 296 支被呼叫的程式原始碼不在舊碼樹（TD、IM、LN、EX 等），需要先補齊或排除範圍。
- 業務裁定：ADR-0008 的待裁定與待簽核偏離，只能由使用者與業務單位決定；FR 第一批（FR1000／FR1010／FR1030）建議先裁定 #32～#39。
- 實測會真的寫入資料庫：只對測試庫執行。
