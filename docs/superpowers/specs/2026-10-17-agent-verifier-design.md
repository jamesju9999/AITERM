# Agent 協作：驗收者角色

日期：2026-10-17
狀態：設計已與使用者確認（2026-10-17），待寫實作計畫

## 1. 為什麼

現在的流程是：工程師做模組 → 審核者看那個模組的 diff → 全部通過 → 協調者合併 →「全部完成」。

- 審核者只看單一模組的改動，看不到模組之間怎麼串。
- 協調者合併後，提示只說「有測試就跑一次」（`workflow::merge_body`）。測試失敗不會退回任何人，頂列照樣顯示全部完成，程式庫也照樣被快轉成整合結果（`fast_forward_repo`）。
- 實例：Pomodoro 各元件都審過，最後把它們串起來的 main.ts 有沒有真的能跑，沒有人驗。

驗收者負責補上這一段：**確認合併起來的成果真的能用**，不能用就退回負責的工程師。

## 2. 使用者已拍板的決定

1. 驗收者是**獨立角色**，不併進協調者。理由跟審核者獨立一樣：剛合併完的人自己驗容易放水。
2. 網頁專案**要開瀏覽器實際操作**。要涵蓋所有應用程式情境（見 §5）。
3. 驗收失敗但**找不出是哪個模組**的問題 → 交給使用者決定，不自動開給工程師。
4. **沒放驗收者就照現在的流程**，舊專案不受影響。

## 3. 角色與卡片

- 新的 Agent 種類 `verifier`（畫面名稱「驗收者」），每個專案最多一位。Agent 池放在協調者右邊。
- 新的卡片種類 `verify`（`workflow::KIND_VERIFY`）。
- 驗收者跟審核者一樣：**不改程式**，在受驗版本的 detached worktree 裡跑（沿用 `prepare_review_worktree` 的作法），判定寫成檔案。
- 建置、安裝相依套件會在那個 worktree 產生檔案，沒關係，那個 worktree 用完即丟，不會 commit。

## 4. 流程

```
全部模組通過 → 協調者合併 → [有驗收者] 建驗收卡（受驗版本 = 合併卡的 end_sha）
                                ↓
                       驗收者驗收，寫 verify.json
            ┌───────────────────┼─────────────────────────┐
          通過             有失敗項，都標了模組          有失敗項，找不到模組
            ↓                      ↓                           ↓
  快轉程式庫、頂列「✓ 驗收通過」   對每個模組開修正卡給原工程師     通知使用者（同 attention）
                                   → 審查 → 合併 → 再驗收
```

### 4.1 什麼時候建驗收卡

- `after_card_finished` 的 `KIND_MERGE if success`：有驗收者 → 建驗收卡，**不快轉程式庫**。沒有驗收者 → 照舊快轉。
- 驗收卡的 `start_sha` / `end_sha`：受驗的整合結果（合併卡的 `end_sha`）。跟審查卡一樣，這兩欄是「建卡輸入」，重試時不可清掉（見 32ad2c43 的教訓）。

### 4.2 通過

- 把程式庫快轉到受驗版本（沿用 `fast_forward_repo`）。快轉結果寫在**受驗的合併卡**的 `verdict`（驗收卡的 `review_of` 指向它），跟沒有驗收者時的位置一樣，頂列判斷不用分兩套。有驗收者時，合併卡的 `verdict` 在驗收通過前是空的。
- 驗收卡自己的 `verdict`：`pass`／`fail`／`attention`（失敗而且要你決定：輪數超過上限，或失敗項全都找不到模組）。
- `?` 需人工確認的項目不擋通過，但頂列寫「✓ 驗收通過（N 項需你確認）」，點開看清單。

### 4.3 不通過

- 每個失敗項如果有 `module_id` 而且對得上一個模組 → 依模組分組，每個模組開一張修正卡給原工程師。
  - 修正卡內文：驗收者寫的重現步驟、預期與實際、截圖路徑，加上模組原始需求。
  - 修正卡 `module_id` = 模組，`review_of` = **模組鏈目前的尾端**（通過的那張審查卡；沒有審查者時是最後一張成功的工作／修正卡）。修正卡內文寫明是哪張驗收卡退回的。
- 修好後照原本的路走：審查 → 模組回到通過 → `maybe_enqueue_merge`（工程師分支 HEAD 變了，signature 不同，會建新的合併卡）→ 再驗收。
- **輪數**：同一輪工作裡驗收失敗超過 `MAX_FIX_ROUNDS`（2）次 → 不再開修正卡，改成通知使用者（沿用 `agent-module-attention` 的通知與「放行」流程，放行 = 視為驗收通過、快轉程式庫）。
- 有任何失敗項找不到模組 → 那些項目不開卡，通知使用者；有模組的照樣開修正卡。
- 失敗項**全部**找不到模組 → 驗收卡 `verdict = attention`，流程停住等你決定（放行或自己處理）。
- 輪數的算法：從最近一次 `pass` 之後，連續 `fail`／`attention` 的驗收卡張數。

### 4.4 模組狀態（實作時要特別小心）

`workflow::module_state` 與前端 `deriveModuleState` 用 `review_of` 串出模組鏈判斷狀態：模組 → 審查 →（fail）→ 修正 → 審查 …，走到審查 `pass` 就停。

驗收退回的修正卡 `review_of` 指向鏈尾（§4.3），所以 `walk` 只要多兩條規則：
- 走到 `pass` 的審查卡時，再找 `review_of` = 這張審查卡的修正卡，有就接著走。
- 找不到審查卡時（沒有審查者），找 `review_of` = 目前這張的修正卡，有就接著走。
這兩種修正卡不算進審查退回的輪數（`fails`）。

要確認：
- 模組本來是 Passed，驗收退回開了修正卡之後，模組狀態要變回「修正中」，不能還是 Passed（否則 `maybe_enqueue_merge` 會在修正前又合併一次）。
- 修正卡的審查卡、再下一張修正卡，鏈要能接上。
- 前後端兩邊規則一致（`deriveModuleState.test.ts` 與 Rust 測試用同一組情境）。

計畫裡要先寫這幾個情境的測試再改。

## 5. 依專案類型的驗收方式

驗收者自己判斷專案類型（看 package.json、Cargo.toml、pyproject 等），照下表做。這張表寫進驗收卡的提示。

| 類型 | 驗法 |
|---|---|
| 網頁前端 | 啟動開發伺服器 → 用瀏覽器工具照驗收條件實際點擊、輸入、換頁 → 檢查主控台錯誤 → 每條條件截圖 |
| 後端 API | 啟動服務 → 實際呼叫端點，檢查狀態碼與內容 |
| 全端 | 前後端都啟動 → 從瀏覽器操作，確認資料存進後端、重新整理後讀得回來 |
| 命令列工具 | 實際執行各種參數，檢查輸出與結束碼 |
| 函式庫 | 跑測試 → 寫一小段程式實際呼叫公開介面（寫在 worktree 外的暫存位置） |
| Electron | 用瀏覽器工具操作 |
| 其他桌面／手機 App（原生、Tauri、iOS、Android） | 只做建置、測試、啟動不當掉；要操作畫面的條件標成 `manual` |

不做電腦操作（接管使用者的螢幕和滑鼠），之後有需要再做成選項。

### 5.1 驗收條件從哪來

提示裡附上：
- 每個模組的 id、標題、需求內文。
- 有規格的專案：規格全文（沿用 `spec_appendix`，有 30,000 字上限），並要求照規格的驗收條件逐條驗。
- 沒有規格：照各模組需求自己列驗收條件，寫進 verify.json。

## 6. 瀏覽器

### 6.1 接法

驗收卡的 `mcp.json` 除了 `aiterm`（ask_human）之外，再加一個 Playwright MCP：

```json
"playwright": {
  "command": "npx",
  "args": ["-y", "@playwright/mcp@0.0.83", "--headless", "--isolated", "--output-dir", "<task_dir>/evidence"]
}
```

`--allowedTools` 加上 `mcp__playwright`（整個伺服器的工具）。

- `--isolated`：瀏覽器設定檔只放記憶體，不碰使用者的瀏覽器資料、登入狀態、cookie。
- `--headless`：不跳出視窗。
- 版本釘死：`0.0.83`（2026-09-28 發布）。工具參數在版本之間會改（實測：`browser_click` 的參數已改成 `target`），不釘死的話某天會突然壞掉。

### 6.2 實測結果（2026-10-17，0.0.83，macOS）

用 JSON-RPC 直接驅動，開本機網頁：
- `browser_navigate`、`browser_snapshot`、`browser_click`（參數 `target` = snapshot 裡的 ref）、`browser_console_messages`、`browser_take_screenshot` 都可用；點擊後畫面確實改變。
- 首次導航約 1 秒（這台有裝 Chrome）。
- **陷阱**：`browser_take_screenshot` 的 `filename` 給相對路徑時，存到 **MCP 行程的工作目錄**，不是 `--output-dir`。MCP 行程是 claude 啟動的，工作目錄就是受驗的 worktree。

### 6.3 待驗證（寫計畫前或計畫第一步要確認）

1. ~~截圖給絕對路徑會不會被擋~~ 已驗證（2026-10-17）：工作目錄與 `--output-dir` 以外的絕對路徑被擋（`File access denied … outside allowed roots`）；**`--output-dir` 底下的絕對路徑可以寫**。所以提示要求截圖一律存成 `<task_dir>/evidence/<名稱>.png` 的絕對路徑，`--output-dir` 就設成那個資料夾，不需要開放任意檔案存取。
2. **沒有裝 Chrome 的機器**：預設用 Chrome，沒有的話會怎樣？要不要改 `--browser chromium` 並在第一次使用時下載（約 150MB）？
   驗證：用乾淨的 HOME、`--browser` 各種值跑 probe。Windows、Linux 各跑一次。
3. 沒有 Node.js（沒有 npx）的機器：驗收者照樣能做非網頁的驗收，瀏覽器工具不可用時要在 verify.json 把需要瀏覽器的條件標成 `manual` 並說明原因，不能當通過。

## 7. verify.json

寫到 `<專案>/tasks/<驗收卡 id>/verify.json`：

```json
{
  "verdict": "pass" | "fail",
  "project_type": "web",
  "items": [
    {
      "criterion": "按開始後倒數 25:00",
      "status": "pass" | "fail" | "manual",
      "module_id": "<模組卡 id，找不出來就省略>",
      "evidence": ["evidence/start.png", "npm test 輸出摘要…"],
      "steps": "重現步驟（fail 時必填）",
      "expected": "…",
      "actual": "…"
    }
  ],
  "notes": "其他觀察"
}
```

- `verdict` 只接受 pass／fail；任何一項 `fail` 就必須是 `fail`（後端檢查不一致時以 items 為準）。
- `manual` 一定要寫原因（例如「需要真實付款」「原生 App 畫面」）。
- 檔案沒寫、或解析失敗 → 驗收卡當成失敗，暫停驗收者（跟 review.json 一樣的處理）。
- 證據路徑相對於卡片資料夾。

## 8. 收尾：伺服器與埠

- 派驗收卡時，App 先找 3 個空閒的埠，寫進提示，要求伺服器只用這些埠。不會跟使用者正在跑的服務搶埠。
- 提示要求驗收結束前關掉自己啟動的伺服器與瀏覽器。
- **保險**：驗收卡結束後（不論成敗），App 找出還在監聽那 3 個埠的行程並結束它們。macOS／Linux 用 `lsof -ti tcp:<port>`，Windows 用 `netstat -ano`。只動這 3 個埠，不碰別的。
- Playwright MCP 是 claude 的子行程，claude 結束時跟著結束。

## 9. 畫面

- Agent 池多「驗收者」，每專案一位。
- 合併卡完成後，連線從協調者畫到驗收者。
- 驗收者卡片：驗收中／✓ 通過（N 項需你確認）／✗ 退回 N 項／⚠ 需要你決定。
- 點驗收卡打開**驗收報告**：每條條件的狀態、重現步驟、截圖縮圖（點開放大）。
- 頂列摘要：
  - 有驗收者時，合併完成但還沒驗收 →「已合併，驗收中」。
  - 驗收通過 → 才顯示「全部完成」那一套（含已更新到程式庫／為什麼沒更新）。
  - 驗收退回 →「驗收退回 N 項，修正中」。
- Token 用量照現有機制顯示（驗收卡算在驗收者身上）。

## 10. 成本

- 用瀏覽器操作很花 token：每一步都會回傳頁面結構（snapshot）。中型網頁專案驗一輪估計一兩百萬 token。
- 驗收者可以在角色設定指定比較便宜的模型（已有功能）。
- Playwright MCP 有 `--snapshot-mode`、`--mobile`（頁面較輕）等選項可以省 token，先不開，等有實際用量數字再調。

## 11. 不做

- 電腦操作（原生 App 畫面）。
- 驗收者自己修 bug。
- 多位驗收者、驗收重點分工。
- 在已部署的網站上驗收（只驗本機啟動的版本）。

## 12. 測試與驗收

- Rust：`verify.json` 解析；合併後有／沒有驗收者的分支；通過時快轉、失敗時依模組開修正卡；找不到模組的項目進 attention；輪數上限；模組狀態在驗收退回後的變化（§4.4）；埠的保險清理（以假行程監聽埠測試）。
- 前端：`deriveModuleState` 的新情境（與 Rust 同一組）；驗收者卡片各狀態；頂列摘要；驗收報告對話框。
- 實機：
  1. 假 claude 腳本跑完整流程（不花額度），包含驗收退回一輪再通過。
  2. 真 claude 驗一個小網頁專案（例如 Pomodoro），確認會開瀏覽器點、截圖出現在報告裡、伺服器有關掉。
  3. 故意留一個串接 bug，確認驗收會抓到並退回正確的工程師。
