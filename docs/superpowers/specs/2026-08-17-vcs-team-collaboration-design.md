# AITerm 版控分頁 — 團隊協作可見度 — 設計

日期：2026-08-17
狀態：待使用者核可

## 問題

2-3 人的小團隊想在同一個 repo 上各自開發不同功能、最後合併，但團隊成員不熟悉 GitHub 操作（branch、PR、merge 這些概念）。

AITerm 現有的「版本控制」分頁（`VcsView`）已經解決了「不用打 git 指令」這件事——整個介面是純自然語言對話，`GitClient`（`src-tauri/src/vcs/git.rs`）已經有 `create_branch`、`create_pr`、`merge_pr`、`branch_list`、`pr_list` 等完整操作。但它是純單人視角的聊天室：

1. **看不到隊友在做什麼。** 沒有任何畫面列出「誰在改什麼功能、動了哪些檔案」。
2. **無法在動手前知道會不會撞檔案。** 兩人同時改到同一個檔案，只能等合併時才發現衝突。
3. **合併要嘛用自然語言下指令、要嘛得去 GitHub 網站。** 沒有一個結構化、按鈕導向的「開始新功能 → 完成送審 → 合併」流程。

## 範圍

**含：**

- 版控分頁新增「團隊可見度面板」：列出目前所有進行中的功能（負責人、狀態、已改動檔案）
- 結構化的「開始新功能」引導流程（表單 → 建分支 → 開 draft PR → 事前重疊檢查）
- 結構化的「完成，送審 → 合併」流程（PR 轉正 → 分頁內顯示完整 diff → 按鈕合併）
- 一個本機 MCP server，讓終端機分頁裡的 Claude Code CLI 也能查詢團隊狀態（`list_active_features`、`check_file_overlap`）
- 全程使用者不會看到 git/GitHub 術語（branch/PR/merge 一律轉譯成「功能」「送審」「合併」等中文口語）

**不含（各自是更大或更冒進的範圍，先不做）：**

- 自動衝突解決（AI 嘗試合併衝突的兩邊）——衝突一律阻擋並提示人工處理
- 強制不能自己合併自己功能的同儕審核門檻——本設計允許自己按合併
- 自訂的「認領清單」檔案或任何新的持久化資料庫——所有團隊狀態即時從 GitHub PR API 取得，不新增本機資料表
- 中央即時同步伺服器（比照 Enterprise 派送任務的架構）——不需要，GitHub 本身就是 A/B/C 三台機器間天然的共享狀態
- 終端機分頁上的視覺徽章提示（brainstorm 中作者原本建議的簡化方案）——使用者選了更完整的 MCP 整合路線

## 決策紀錄

以下是使用者在 brainstorm 中明確選定的，其中一項與作者原本建議相反，實作時不要「順手改回來」：

| 決策 | 選定 | 作者原本建議 |
|---|---|---|
| 三種架構方案 | **A：完全靠 GitHub 本身當共享狀態，不建新伺服器** | 同（推薦並採納） |
| 衝突處理策略 | **事前防範（開始前提醒重疊檔案）＋ 合併時真的衝突就阻擋人工處理** | 同 |
| 合併體驗 | **AITerm 內按鈕直接審核＋合併，完全不用去 GitHub** | 未表態，使用者主動選了最完整的一項 |
| 終端機分頁如何得知團隊狀態 | **B：MCP 整合，讓 Claude Code CLI 能直接查詢** | A：終端機分頁上加簡單徽章提示（風險低、重用現有 cwd 追蹤機制） |
| 合併權限 | **允許自己合併自己開的功能，不強制換人審** | 未表態，二選一問使用者 |

## 架構

### 放置位置與用語

不新增分頁，長在既有的「版本控制」分頁（`VcsView.tsx`）裡，聊天框上方新增一塊面板區。全程使用者不會看到 git 術語：

| 內部概念 | 使用者看到的字 |
|---|---|
| 建立 branch + 開 draft PR | 「開始新功能」 |
| 列出 open/draft PR | 「進行中的功能」 |
| PR 轉正（ready for review） | 「完成，送審」 |
| `merge_pr` | 「合併」 |

### 開始新功能

1. 使用者按「開始新功能」，跳出表單：功能名稱（自由文字）＋ 選填「預計會動到的檔案或範圍」。
2. 送出後 AITerm 依序執行：
   a. 用既有的 `GitClient::create_branch` 建立並切換到新分支，命名規則 `feature/<slug>-<github-username>`（slug 由功能名稱轉英數，使用者不會看到這個原始名稱）。
   b. 若使用者填了「預計檔案」，比對其他目前 open 的功能已經**實際改過的檔案**（來自 GitHub diff，非其他人自己宣告的範圍）是否重疊；有重疊就跳警告，使用者可選「仍要開始」或「取消，先溝通」。
   c. 沒有衝突（或選擇忽略警告）後，用既有的 `GitClient::create_pr` 開一個 **draft PR**，title 帶功能名稱、body 附上「預計檔案」說明，讓它立即出現在團隊可見度面板與 `list_active_features`。
3. 完成後提示：「已開始『<功能名稱>』，這個分頁現在在這個功能的分支上工作」。

**已知限制**：若使用者沒填「預計會動到的檔案」，開始當下沒有任何範圍可比對，事前防範這次就防不了——只能等使用者實際 commit 後，團隊面板下次重新整理時才會事後偵測到重疊。這個限制要在 UI 文案裡老實告知，不假裝能做到 100% 事前攔截。

此引導流程只處理「從零開始一個新功能」；使用者若原本就手動在某分支工作，不受此流程接管，可繼續用既有的自然語言對話介面操作。

### 團隊可見度面板

版控分頁聊天框上方的新面板，列出目前所有進行中的功能：功能名稱、負責人、狀態（進行中／待審核）、已改動檔案（可展開）。資料來源是延伸既有的 `GitClient::pr_list`（目前的 `PrEntry` 缺 `draft` 狀態與改動檔案清單，需要擴充），加上一支新的「取得單一 PR 改動檔案清單」呼叫（GitHub `GET /repos/{owner}/{repo}/pulls/{number}/files`）。

更新時機：分頁取得焦點時自動抓一次，另外提供手動「重新整理」按鈕。不做即時推送（不需要為此開伺服器或用 WebSocket）。

### 完成，送審 → 合併

1. 使用者在自己名下的功能上按「完成，送審」：
   - 呼叫新增的 GitHub API 操作，把 draft PR 轉為 ready for review。`GitClient` 目前沒有這個方法，需要新增；確切要打 REST 還是 GraphQL（GitHub 的 draft→ready 轉換 REST 支援度需要在 writing-plans 階段實測確認）留到那時候決定，本 spec 只定義行為：使用者按下後，該 PR 從「進行中」變成「待審核」狀態。
2. AITerm 在分頁內顯示這個功能完整的 diff（整個分支相對主線的差異，不是單一 commit）——現有的 `show`/`view_diff` 只能看單一 commit，需要新增一支「取得 PR 完整 diff」的方法（GitHub compare 或 PR diff 端點，實作時確認）。
3. 看完按「合併」→ 呼叫既有的 `GitClient::merge_pr`。
4. 合併成功後，詢問是否要一併刪除這個功能分支（呼叫既有的 `GitClient::delete_branch`）。
5. 若 GitHub 回報這個 PR 有衝突無法合併，直接顯示「有衝突，需要先手動處理」並中止，不嘗試自動解決。

合併權限：任何團隊成員都可以按合併，包含合併自己開的功能——不強制換人審核（對兩三人團隊而言，同儕審核門檻太重）。

### MCP 整合（終端機分頁的 Claude Code CLI 也能查）

AITerm 本機常駐一個小型 MCP server，開放兩個工具：

- `list_active_features`：列出目前 repo 裡團隊所有進行中的功能（作者、標題、已改動檔案）
- `check_file_overlap(files: string[])`：傳入即將要改的檔案清單（repo 相對路徑，逐一精確比對，不做目錄/glob 比對），回傳跟誰的功能重疊

資料來源與團隊可見度面板共用同一套（都是走上述擴充後的 GitHub PR API 呼叫），不會有兩份對不上的資料。AITerm 會在使用者於某個 repo 使用過「開始新功能」流程後，自動為該 repo 準備好 MCP 設定，讓該資料夾下啟動的 Claude Code CLI 自動接得到這兩個工具，使用者不需要手動設定 `.mcp.json`。

**降級行為**：若 AITerm 沒有在執行中（例如使用者不透過 AITerm、直接在系統終端機開 Claude Code CLI），這兩個工具就連不到，Claude Code CLI 端該次工具呼叫失敗、正常繼續對話——不會因此掛掉或卡住整個 session。

MCP server 的確切傳輸方式（stdio / 本機 HTTP+SSE）與 `.mcp.json` 該寫入 repo 內（共用）或使用者本機設定（不共用進 git）留給後續 writing-plans 階段決定，本 spec 只定義行為契約：兩個工具的輸入輸出、以及「AITerm 沒開著就優雅降級」這個不變式。

## 錯誤處理

沿用版控分頁現有的錯誤處理模式，不重造一套：

- 沒設定 GitHub token／目前目錄不是 git repo → 沿用既有的 `vcs_no_token`／`vcs_no_repo` 提示文案，導向設定頁。
- 「開始新功能」時分支名稱衝突（例如兩人打了非常相似的功能名稱）→ 照實顯示 git 回傳的錯誤，請使用者重新命名。
- PR 轉正、合併失敗（GitHub 回衝突或其他錯誤）→ 照實顯示錯誤訊息，不吞掉、不嘗試自動修復。
- MCP 工具呼叫連不到本機 AITerm 服務 → 該次工具呼叫回傳失敗，Claude Code CLI 端正常繼續，不視為致命錯誤。
- 使用者「開始新功能」時沒填「預計檔案」→ 不是錯誤，是已記錄在案的功能限制（見上）。

## 測試

比照專案既有慣例：

- **Rust**：新增的 `GitClient` 方法（PR 轉 ready-for-review、取得 PR 完整 diff、`pr_list` 擴充後含 draft 狀態與改動檔案）用 `wiremock` 假造 GitHub API 回應測試，比照 `src-tauri/tests/knowledge_base_embedding.rs` 的寫法。
- **Rust**：檔案重疊比對邏輯寫成不碰 HTTP 的純函式，單元測試涵蓋「有重疊」「沒重疊」「一方沒填預計檔案」「大小寫/路徑正規化差異」等情境。
- **前端**：新的「開始新功能」表單、團隊可見度面板、送審/合併畫面用 Vitest + Testing Library，mock IPC 呼叫，比照 `src/components/KnowledgeBaseView/NotebookSidebar.test.tsx` 的寫法。
- **MCP server**：`list_active_features`、`check_file_overlap` 兩個工具各自寫整合測試確認回傳格式；另外測「AITerm 服務不可用」時的降級行為（工具呼叫應乾淨失敗，不掛住呼叫端）。
