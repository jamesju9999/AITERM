# Agent 協作：批次卡片（草案）

日期：2026-11-02　狀態：草案，等使用者確認範圍後再寫實作計畫

## 為什麼

舊平台轉換（EGL＋Ares → 網頁）的盤點是 533 支畫面、641 支後端程式。這些工作是**同一種骨架、不同參數**，
主手冊 `egl-ares-web-migration` 也說明要靠產生器，不能一支一支手寫。

現況（`tasks/workflow.rs` 的 plan 卡）：協調者讀規格，輸出 `{"tasks":[{title, body, depends_on}]}`，
每一項變成一張模組卡、各自派一位工程師、各自審核。拆成數百張卡的問題：

1. 協調者要輸出數百筆 JSON，單次輸出放不下，拆解本身會失敗。
2. 每張卡各開一個 session，重複讀同一份技能與規格，token 成本跟張數成正比。
3. 畫布與看板被數百張幾乎一樣的卡片淹沒，看不出整體進度。
4. 審核者每張卡審一次，數百次審核，沒有「抽樣審」或「整批審」。

## 目標

一張**批次卡**代表「同一份工作方式 × 一份清單」。一位工程師分梯次處理清單，進度以「項目」為單位記錄，
整批審核一次或抽樣審核，畫布上只出現一張卡。

非目標：不改單張模組卡的流程；不做跨批次的自動排程優化；不處理清單產生（清單由分析師或使用者提供）。

## 設計

### 資料

`tasks` 加一欄 `batch`（JSON，NULL＝一般卡）：

```json
{ "template": "依 htbtw-screen 的契約產生畫面 renderer，驗證方式見 body",
  "chunk": 20,
  "items": [{"key": "Cm1000", "note": ""}, ...] }
```

進度另放一張表 `batch_items(task_id, key, status, note, updated_at)`，`status`：`todo | done | skip | failed`。
不把進度寫回 `batch` JSON，避免每個梯次改寫整份清單。

### 執行

1. 排程器派這張卡時，只把**下一梯次**（`chunk` 筆 `todo`）交給工程師，提示附 `template` 與這一梯次的清單。
2. 工程師完成每個項目後，寫入 `<專案>/tasks/<id>/batch.json`（跟 `verify.json` 同樣位置與做法）：
   `{"done": ["Cm1000"], "skip": [{"key":"Cm1010","why":"…"}], "failed": [{"key":"…","why":"…"}]}`。
3. 這一梯次結束時，把 `batch.json` 併進 `batch_items`；還有 `todo` 就**同一張卡重新排隊**，開新 session 做下一梯次；
   全部非 `todo` 才進入審核。
4. 防呆：連續兩個梯次沒有任何新的 `done`／`skip`／`failed`，就把 Agent 暫停（沿用 `paused_task_id` 與
   「需處理」畫面），避免空轉燒 token。

### 審核與驗收

- 審核者看的是**整批 diff**，審核提示額外附「抽樣規則」：失敗項目全看，其餘依 `chunk` 抽樣（預設每梯次 3 項）。
- 有 `failed` 項目時，審核通過後自動產生一張「修正批次卡」，清單只含失敗項目，沿用同一份 `template`。
- 驗收者不變：驗收條件在規格裡，對整體網站驗，不是逐項。

### 畫面

- 批次卡在工程師卡上顯示為一顆 chip：`Cm 畫面 ▓▓▓░ 342/533`，點開看項目清單（全部／待做／失敗），失敗項可個別「重做」。
- 頂列摘要與收尾卡把批次進度算進「模組 x/y」。
- 活動記錄每個梯次一行，不逐項。

### 建立方式

1. 輸入列貼清單（每行一個 key）並選「批次」。
2. 分析師的規格裡寫 ```` ```batch ```` 區塊，協調者拆解時辨識（只拆出 batch 的 `template` 與清單，不展開成數百筆 JSON）。
3. 匯入檔案（例如 `htbtw-screen` 產出的 `*-screens.json`）：選檔案並指定哪個欄位當 key。先做 1 與 3，2 之後再說。

## 對舊平台轉換的對應

| 路線圖階段 | 用批次卡做什麼 |
|---|---|
| 盤點 | 每個模組一個項目，輸出 `docs/inventory/<模組>.md`（目前是三位研究工程師各一份，不是批次） |
| 後端 | 641 支程式契約 → 產生器輸出，一梯次 20 支 |
| 畫面與流程 | 533 支畫面契約 → renderer，一梯次 20 支，失敗項目另開修正批次 |
| 驗證 | 不用批次，驗收者逐條件驗 |

**不適合批次的部分**（要人決定、或一次性）：立案、執行期語意實測、殼層（登入／選單／權限）。這些維持單張卡。

## 風險與未驗證

- **品質隨批量下降**：一個 session 連做 20 項，後面的項目可能偏離前面的做法。`chunk` 要實測決定；預設 10 比較保守。
- **審核抽樣可能漏錯**：規則「失敗全看、其餘抽樣」只在失敗項目有被如實回報時成立。工程師把有問題的標成 `done` 就會漏。
  需要驗收者的整體驗證當第二道網。
- **上下文累積**：同一張卡多個梯次要不要沿用同一個 session（省 token、但上下文會滿）還是每梯次新開（乾淨、但要重讀）。
  草案選每梯次新開；需實測。
- **`batch.json` 協議**：Agent 可能寫錯格式或漏寫。沿用 `verify.json` 的做法：格式錯誤算該梯次無進度，觸發上面的防呆。
- **並行**：一張批次卡一次只有一位工程師做。想要多位平行就拆成多張批次卡（依範圍分，例如 cm／ac 各一張），草案不做同一張卡的多人平行。
- 我還沒有量過：單張卡處理 20 項要花多少 token、多久，以及協調者輸出的 JSON 實際上限。實作前要先做一次小規模試跑（5 支畫面）取得數字。

## 實作切分（估）

1. 後端：`batch` 欄位與 `batch_items`、梯次派工與重新排隊、`batch.json` 解析與防呆（含測試）。
2. 審核提示附抽樣規則；修正批次卡的自動產生。
3. 前端：批次 chip 與項目清單、輸入列的「批次」入口（貼清單／匯入檔案）。
4. 驗收：以 5 支畫面的垂直切片在真實專案試跑一次。

## 待使用者決定

1. 每梯次預設筆數（建議 10）。
2. 失敗項目要不要自動產生修正批次卡（建議要）。
3. 要不要先做「匯入 `*-screens.json`」還是只做貼清單。
