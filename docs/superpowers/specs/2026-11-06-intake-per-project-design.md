# 問題收集依專案分流 — 設計規格

**日期：** 2026-11-06
**狀態：** 待使用者核可（核可後再寫實作計畫）
**前置：** `2026-11-05-intake-queue-design.md`（目前全部問題集中在一份清單、一組設定）
**範圍：** 只做「專案分流」。問題直接變成看板卡片、進 Agent 協作派工留給下一期；本期保留 `project_id` 作為之後接軌的鍵。

---

## 1. 問題

目前所有來源（信箱、Telegram、網頁表單）的問題都進同一份清單、共用一組別名／主旨標籤／白名單。多個專案時：

- 看不出一個問題該由哪個專案處理；
- 每個專案的關鍵字、信箱、驗證指令不同，卻只能設一組；
- 終端機分頁領到的問題可能不是它所在專案的。

## 2. 決策

| # | 決策 | 理由 |
|---|---|---|
| D1 | 「專案」＝工作看板的專案（`ProjectRegistry`，`.aitprj`）。問題收集上方加專案選擇器，做法同 Agent 協作 | 使用者指定；與看板、Agent 協作同一個專案概念，下一期才接得起來 |
| D2 | 資料仍放全域 `intake.db`，各表加 `project_id` | 信件入庫時要一次比對所有專案的別名／標籤，專案資料夾可能關閉或遺失；白名單與信箱位址不該隨專案資料夾被複製出去 |
| D3 | **每專案獨立**：啟用、收信帳號、辨識方式、別名、主旨標籤、驗證結果來源、內外部派送與回覆層級、每小時上限、驗證指令與逾時、白名單、問題清單。**全域共用**：網頁表單伺服器的埠與模式、Telegram 機器人 | 後兩者是單一實體（一個埠、一個 bot），無法各專案各開一份 |
| D4 | 信件歸屬＝比對各「已啟用」專案的別名／標籤／專用信箱，**符合哪個就進哪個**；都不符合丟棄（同現在，不計數） | 使用者要的是依專案的關鍵字分流 |
| D5 | 儲存設定時**檢查唯一性**：同一信箱帳號下，別名不可與另一個已啟用專案相同、主旨標籤不可相同；專用信箱模式一個帳號只能給一個專案。違反就拒絕儲存並指出衝突的專案 | 讓歸屬永遠只有一個答案，不需要「符合多個怎麼辦」的規則 |
| D6 | 寄件者要在**該專案**的白名單內；信符合專案 A 的標籤、但寄件者不在 A 的白名單 → 記在 A 的丟棄計數，不會跑去別的專案 | 白名單是專案內的授權，不跨專案 |
| D7 | 終端機分頁按「啟動問題收集」時**選專案**，預設帶入「分頁工作目錄落在哪個專案的 `repo_dir` 之下」，找不到再帶入目前選擇器的專案。分頁只領取所選專案的問題；一個專案可有多個分頁 | 使用者指定「每個專案目錄固定」；分頁與專案一對一，派工不會串錯 |
| D8 | 分頁工作目錄不在所選專案的 `repo_dir` 之下時**警告但不擋**（專案可橫跨多個 repo） | 專案不綁定單一目錄（看板專案化 D1） |
| D9 | 驗證沿用現有機制（派工前後內容指紋＋該專案的測試指令），工作目錄仍取分頁的目錄 | 不重做；只是測試指令改取自專案設定 |

## 3. Telegram 與網頁表單怎麼歸屬

兩者本身沒有「主旨標籤」可比對，改用**授權名單所屬的專案**：

- **Telegram：** 聊天室必須在某專案的白名單（`tg:<id>`）內，問題就進那個專案。同一個聊天室出現在多個專案時，訊息要寫成 `/ask 專案名稱 問題內容` 指定；沒寫且有歧義就回覆「請指定專案」。主人自己的 `/ask`：可指定專案；沒指定則用設定裡的「Telegram 預設專案」。
- **網頁表單：** 網址帶專案，`http://<host>:<port>/p/<專案短代碼>`；頁面標題顯示專案名稱，驗證碼與白名單都只查該專案。首頁 `/` 列出已啟用網頁表單的專案連結。伺服器在「任一專案啟用網頁表單」時啟動；任一專案設為區網則綁 `0.0.0.0`（維持現有的警告）。

## 4. 資料模型

`intake.db` 變更（以現有 `init_schema` 逐欄補的方式遷移）：

- `intake_items` 加 `project_id TEXT NOT NULL DEFAULT ''`；索引改 `(project_id, status, created_at)`。
- `intake_senders`：主鍵改 `(project_id, address)`。
- `intake_dropped`：主鍵改 `(project_id, reason)`；`project_id=''` 放「無法判定專案」的計數。
- `intake_settings` 的單一 `config` 列 → 每專案一列（key `config:<project_id>`）。全域項目（網頁表單埠、Telegram 預設專案）放 key `global`。
- `message_id` 的唯一性維持全域（同一封信不會因為歸屬不同而重複入庫）。

### 既有資料

- 升級後既有的題目、白名單、設定的 `project_id` 為 `''`。
- 啟動時若只有**一個**專案，自動歸給它；有多個專案則選擇器多一個「未歸屬」項目，列出這些題目，可逐題或全部「指派到專案」、或刪除。設定與白名單則在使用者第一次打開某專案的設定時，提供「從既有設定複製」。
- 遷移不刪除任何原始資料。

## 5. 畫面

- 標題列：信封圖示＋「問題收集」＋**專案選擇器**（下拉，列出開啟中的專案；有未歸屬資料時多一項）；選項旁顯示該專案待處理題數。選擇存在 `localStorage`。
- 清單、設定、白名單、丟棄計數都只顯示所選專案的。設定頁最上方註明「正在編輯：〈專案名稱〉」。
- 儲存設定遇到唯一性衝突時，在欄位旁顯示「與專案〈名稱〉重複」。
- 終端機工具列的「啟動問題收集」：點下去先出現專案選單（預設專案已選好），確認後顯示「收集中：〈專案名稱〉」。

## 6. 後端改動

- `config`：`Config` 加 `project_id`，`load/save` 改為依專案；新增 `GlobalConfig`（網頁埠與模式由「任一專案」推得，不另存；只存 Telegram 預設專案）。
- `rules`／`mail_source`：`ingest` 改為「載入所有已啟用專案設定 → 逐一 `decide`」，取第一個非 `NotForUs` 的結果；有結果才入庫並帶 `project_id`。
- `queue::enqueue`、`store::insert_item`：帶 `project_id`；限流改成「每專案每寄件者」。
- `store::claim_next(project_id, tab)`；`dispatcher::Registry` 的分頁記錄加 `project_id`；`tick` 只把某專案的問題派給該專案的分頁。
- `telegram_source`、`web`：依第 3 節歸屬；網頁表單加 `/p/<代碼>` 路由與首頁。
- 指令：`intake_get_config`／`intake_set_config`／`intake_senders` 系列／`intake_list`／`intake_dropped` 都加 `project_id` 參數；新增 `intake_assign_project`（指派未歸屬題目）、`intake_projects_summary`（各專案待處理題數）。
- 專案資訊（名稱、`repo_dir`）從 `ProjectRegistry` 取；專案被移除時，其問題與設定保留但標為未歸屬。

## 7. 不在本期

- 問題變成看板卡片、進 Agent 協作派工（下一期，以 `project_id` 接軌）。
- 專案設定隨專案資料夾匯出／匯入。
- 跨專案移動已處理完的題目（只提供未歸屬 → 專案的指派）。

## 8. 測試

- **歸屬：** 兩個專案不同標籤共用一個信箱，信各進各的；都不符合丟棄；同標籤的第二個專案存不進去（唯一性）；專用信箱一帳號一專案。
- **隔離：** 專案 A 白名單內的寄件者寄到專案 B 的標籤 → 記為 B 的 `not_allowed`；限流各專案獨立。
- **派送：** 專案 A 的分頁領不到專案 B 的題目；分頁目錄不在專案 `repo_dir` 下只警告。
- **Telegram／網頁：** 聊天室只在一個專案白名單時自動歸屬；多專案時需 `/ask 專案名稱`；`/p/<代碼>` 只查該專案白名單。
- **遷移：** 舊資料庫升級後資料完整；單一專案自動歸屬；多專案時進「未歸屬」。
- **畫面：** 選擇器切換後清單與設定跟著換；衝突提示；工具列選專案。
- 維持現有的假 claude＋假信箱演練，擴成兩個專案各一組別名／標籤，驗證分流與派送不串。
