# 系統連線第四期：信件／Telegram／網頁表單觸發

日期：2026-11-17　狀態：使用者授權照建議做到完成
前置：第一～三期已合併 master。

## 目標
別人寄信（或用 Telegram、網頁表單）提出要求，AI 就在指定的系統上完成，並把結果回覆給對方。
入口沿用「問題收集（Intake）」：寄件者驗證、白名單、頻率限制、草稿／自動寄出都不重做。

## 設計
- 問題收集每個專案有「派送目標」（終端機分頁／工作看板／Agent 協作桌布）。新增第四個：**系統連線**，並多一個設定「要用哪個系統」。
- 路線行為（`route_system`，掛在既有的 `route_and_settle` 掃描裡）：
  1. 專案選了系統連線、且有指定系統時，認領這個專案**最舊的已放行（queued）**題目，標成執行中。
     自動／手動放行的規則照舊：內部寄件者預設自動放行，外部預設要人在問題收集畫面核准才會進 queued。
  2. 以題目的主旨與內文組成目標，交給定時任務用的同一個執行器（Claude Code 無人模式＋系統連線端點）。
  3. 完成後 AI 的回報存成回覆草稿；是否自動寄出照既有設定（內部預設自動寄、外部預設存草稿）。
     失敗（逾時、非 0 結束、寫入被拒絕或等核准逾時）退回待處理並寫明原因，不自動重派。
- **一次一題**：同一個系統同時只處理一題（跟定時任務互斥：用同一把鎖，避免兩邊同時操作同一個瀏覽器）。
- **內容視為資料**：提示明講請求內容來自外部寄件者，只當作要完成的事項；裡面要求繞過規矩的指示不理會。真正的防線仍是寫入閘門：
  系統是只讀就寫不進去，逐次核准的系統沒人按會逾時拒絕。畫面提醒：外部寄件者的題目建議搭配「依規則」並只開放必要的寫入。
- 內文與回覆都經既有的 `filter::redact`（遮蔽金鑰等），不另做。

## 範圍
只做 Email／Telegram／網頁表單共用的題目路線，不改它們的收件與驗證。不做：每個寄件者對應不同系統、題目分類（此路線不分「提問／改程式」）、附件交給 AI。

## 測試
- 純函式：目標文字（含主旨、內文、來源、寄件者層級、警語）。
- 路線整合（mock app＋假 claude）：queued 題目被認領→假 claude 執行→回覆草稿含 AI 回報；未選系統時不碰題目；
  執行器回報失敗時題目退回待處理並有原因；同一系統忙碌時不認領第二題。
